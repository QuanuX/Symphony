# Linux Secret Service native SDK

This optional C++26 library implements the Linux item backend for SSIAG. A native caller can provision binary credentials into an explicitly selected unlocked collection, use one exact generation inside a callback, and retire one generation. The Go SSIAG service currently has no public Linux credential dispatch route.

## Build, exercise and install

Use CMake 3.30 or newer, a C++26 compiler, pkg-config and libsecret 0.21.2 or newer on Linux. The development package on Ubuntu is `libsecret-1-dev`. The isolated integration uses `dbus-daemon`, `libglib2.0-bin`, `gnome-keyring`, and an ordinary non-root UID. Run from this directory in the source checkout:

```sh
build=$(mktemp -d)
prefix=$(mktemp -d)
cmake -S . -B "$build/sdk" -DCMAKE_BUILD_TYPE=Release -DCMAKE_INSTALL_PREFIX="$prefix"
cmake --build "$build/sdk"
ctest --test-dir "$build/sdk" --output-on-failure
cmake --install "$build/sdk"
cmake -S tests/installed -B "$build/consumer" -DCMAKE_PREFIX_PATH="$prefix"
cmake --build "$build/consumer"
timeout -k 5s 40s bash tests/private-session.sh "$build/consumer/installed-consumer"
cmake --build "$build/sdk" --target uninstall-ssiag-linux-secret-service
```

The test starts its own D-Bus daemon and GNOME Keyring process, creates a temporary login collection under a private directory, stores newly generated bytes, and removes the session on exit. Production builds can specify `-DBUILD_TESTING=OFF`. Consumers use `find_package(SymphonySSIAGLinuxSecretService 0.1.0 EXACT CONFIG REQUIRED)` and link `Symphony::SSIAGLinuxSecretService`. Installation emits a versioned receipt and supports guarded uninstall.

## Provider integration

`linux_secret_service.hpp` accepts a collection object path, an installation (TOPS) UUID, a credential reference UUID, and a `GCancellable` owned by the caller. The `Scope` fields and generated generation UUID are nonsecret lookup metadata. Keep identifiers opaque. The caller chooses the actual collection in trusted configuration; `/org/freedesktop/secrets/collection/login` is one GNOME example. Each invocation opens a private connection to the validated Unix socket in `DBUS_SESSION_BUS_ADDRESS`, including when GLib has cached a different live session bus. It resolves the unique connection that owns `org.freedesktop.secrets`, checks its Unix UID, pins that destination for the operation and requires the encrypted Secret Service session algorithm. A locked collection or a prompt is refused. An absent desktop bus or service is unavailable.

- `provision` creates a new generation and returns its exact reference. The accepted credential size is 1–4,096 bytes. The owner must record the reference before selecting that generation for use. On an indeterminate result preserve its returned reference for reconciliation. A process crash before the owner records the reference may leave an orphan and needs owner-level recovery.
- `use` selects the collection, schema, TOPS, reference and generation. It rejects multiple matches, bounds the bytes presented to the consumer, and invokes the supplied callback at most once per call. The view expires when the callback returns. The library maps callback exceptions to `indeterminate`. The byte ceiling applies to the callback, after libsecret receives the service response.
- `retire` deletes one unambiguous match. Repeating retirement after a successful delete returns `not_found`. To replace a credential, provision a distinct generation, commit the owner's selection and retire the previous one explicitly.

The caller must supply a trusted per-user desktop session and service, enforce the lease and recipient, serialize mutations of its item namespace, cancel on deadline, enforce a hard process/time bound if necessary, and durably account for outcomes. Each invocation resolves the service anew. A same-user program with access to this desktop vault may read or change items; attributes identify records and do not authenticate callers. Secret Service searches and subsequent reads/deletes are separate requests, so concurrent independent writers cannot be excluded by this backend. A repeated API invocation is a new call. The SDK makes no claim of durable one-shot delivery, atomic revocation, control of third-party memory copies, or headless/system identity support. Status codes and test logs contain no credential data.
