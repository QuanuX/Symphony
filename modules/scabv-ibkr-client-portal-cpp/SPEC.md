# IBKR Client Portal read adapter: exact 0.1.0-dev contract

## Supported extent

Distinct Client Portal v1 HTTP surface observed 2026-09-28. Requires an already authenticated local Gateway with a trusted TLS certificate at an explicitly selected https://localhost:port or https://127.0.0.1:port. Account discovery GET /v1/api/portfolio/accounts precedes a binding; the selected account must appear once in the bounded response and scope must use this profile’s private: reference grammar. Admission of caller-supplied bytes does not authenticate them. Read plans expose only GET portfolio/{account}/positions/{page} and iserver/marketdata/history. Position pages are 0–9,999, with at most 100 records, exact acctId and nonduplicated conid. An empty page indicates exhaustion; nonempty pages expose the next page. Each request remains partial evidence, not an atomic multi-page account snapshot. Historical plans require conid, explicit UTC startTime, period/bar, direction=-1, source=Last and explicit regular-hours choice. Local bar cap is 1–1,000; provider interval/entitlement rules still apply. Selected numeric fields and increasing bar timestamps are shape-checked, while every original JSON byte—including financial decimals and additional provider fields—is retained. No binary-float reserialization occurs.

## Host session ownership

The optional `Session` uses an explicit `GatewayTransport`; `HttpsGatewayTransport` delegates to the existing verified HTTPS fetch. Injected transports are trusted host code and do not establish provider authenticity. The only added operation is the documented read-only `POST /v1/api/iserver/auth/status`, with no body, credentials or session mutation. Existing account/position/history routes remain GET. Status must report boolean authenticated/connected true and competing false; if established is present it must be true. Missing or malformed fields refuse. No login, tickle, reauthentication or session takeover is dispatched.

Open probes status then discovers accounts. Before each data read it repeats status and selected-account membership checks, constructs a plan and performs its bounded data GET. Caller-controlled plan substitution is not exposed by this host API. HTTP 401 marks expiry; 403 marks refusal without asserting why the provider refused. False authentication or competing-session status closes admission. Other transport, malformed-data or HTTP errors fail the Session without retry. A caller-selected lifetime cap of 1–300,000 ms bounds local admission and request deadlines; it does not predict provider expiry. The status/account/data sequence is not atomic, so the final read can still expire and be refused. Sessions serialize reads and reserve at least five seconds after each completed account-discovery request, including open before the first data read. Early attempts return `limit` before status or data I/O. This implements the selected [one account-discovery request per five seconds limit](https://www.interactivebrokers.com/docs/web-api/v1/pacing-limitations); global Gateway pacing across host sessions remains the host owner's responsibility. Pagination is explicit and each page remains partial evidence.

The host serializes all methods and keeps the transport alive; a transport cannot reenter Session. Forked children refuse. Failed reads preserve the caller's Page. Open preflight failures preserve output; attempted open failures retain failed Session state. Local close forgets admission only; it never logs out the provider. Reopening requires a fresh Session and external authorization remains required. The generic low-level Binding/Plan/Page and connect/collect interfaces remain available under their original contracts.

The status method and fields were checked against [IBKR's current brokerage status reference](https://www.interactivebrokers.com/docs/web-api/api-reference/trading/trading-session/get-brokerage-status). Historical GET examples do not override this exact POST profile. [IBKR's authentication FAQ](https://www.interactivebrokers.com/docs/web-api/authentication/faq) describes independently changing authentication and connection state; the local lifetime cap does not replace provider checks.

## Native/package boundary

C++26, initially verified on macOS amd64 / AppleClang 21 with compatible native consumers. Fallible preparation/admission preserves output on failure unless the API explicitly reports an attempted operation. Immutable handles may be retained; mutation, reset, destruction and move must not race use of the same handle. Source data is untrusted. Errors contain status only, never source contents or credentials. Dependencies: native-source-support-cpp 0.1.0-dev, sqav-capture-cpp 0.2.0-dev. No runtime discovery or implicit upgrade. The module exports no standalone process or qxctl command.

## Verification and limits

`tests/test.cpp` exercises supported positive and negative boundaries; `tests/sdk-consumer/main.cpp` exercises the installed public API outside the checkout. The SQV non-live source composition tests preserve selected capture evidence through exact local retention/replay. The tests and package receipts do not establish provider access, production conformance or a licence grant.

No session login, account mutation, order entry, OAuth replacement, TLS bypass, TWS protocol, atomic account snapshot, production entitlement/conformance claim or operational SSIAG authorization.
