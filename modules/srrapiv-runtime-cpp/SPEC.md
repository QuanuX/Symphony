# SRRAPIV native runtime specification

## Identity and source

Module `srrapiv-runtime-cpp`, engine `symphony-srrapiv`, version `0.1.0-dev`, vector `srrapiv`. First-party native code uses C++26. The supplied vendor baseline is R API+ C++ 13.7.0.0 with header SHA-256 `b996e76fbfe20c7f4d7ba2d645c45cb13d6b19df37d7522125e94e61e74df5b4`. Vendor headers, libraries, private credentials and sample account data are not bundled in this repository.

## Finite administrative interface

One bounded `symphony.knowledge.engine-process.v1` request on stdin produces one correlated response. The payload protocol is `symphony.srrapiv.request.v1`. `OWNER-INTERFACE.json` records the actual eleven native operations: catalog_inspect, binding_validate, binding_compare, coverage_assess, api_describe, runtime_start, runtime_status, runtime_invoke, runtime_events, runtime_stop and runtime_attempts. All are routed through `qxctl sqv rithmic`; schema/template routes expose the installed contract. The result protocol `symphony.srrapiv.result.v1` binds operation, exact engine version, canonical request digest and omit-self result digest.

The finite process request bound is 1 MiB and response bound 4 MiB, with at most 65,536 JSON values and depth 64. Requested finite deadlines are at most 30 seconds ahead. Resident local control frames are bounded to 1 MiB and 65,536 JSON values, with an absolute three-second receive deadline. A caller deadline bounds observation; it does not cancel an admitted SDK operation. Unknown fields are rejected at owning contracts. The shared transport accepts no floating-point JSON numbers or integers beyond interoperable signed 53-bit range. Vendor mappings use exact decimal/bit encodings. `api_describe` reports the version-specific public schemas and mapping dispositions; it does not connect to Rithmic.

## SDK mapping

`src/vendor.hpp`, generated descriptors and native codecs define the explicit bridge. Public overload IDs retain declaration ordinal as `REngine.method#N`; changing SDK declarations requires a separate reviewed mapping/build. Callback observations deep-copy vendor-owned fields before callback return and preserve native string lengths, numeric widths and presence. Process-local pointers require opaque owner handles or explicit scoped adaptation, never caller-supplied addresses. Secure credential inputs resolve references from protected native configuration; getters use protected destinations rather than ordinary result values. SDK-less invocation reports unavailable, not successful execution.

## Local runtime profile

`runtime_start` accepts an absolute private `runtime_dir` and existing private `config_file`. The configuration carries a structurally valid immutable catalog/binding, optional supplied compatibility evidence, vendor engine configuration, protected secrets, allowed_methods and explicit allow_provider_calls/allow_trading policy. Structural validity permits a local host to start with unknown external qualification; it does not authorize automatic login. Native initialization and vendor calls require explicit invocation.

A child process starts a new session and detaches inherited standard streams. The server acquires an exclusive owner lock and listens on a mode-0600 Unix-domain socket inside its uid-owned mode-0700 directory. Client and server check peer uid and the exact adapter executable digest in the local control handshake. Private file reads and atomic writes traverse no-follow directory descriptors; ancestors must be trusted and final storage private to the current uid. Root-owned sticky temporary parents are permitted. The first profile supports the current local OS user only, with no remote carrier or delegated multi-user authority claim. Generations identify one runtime incarnation. A new live owner is never displaced by start. Initialization failures after acquiring the owner lock can retain runtime-failure.json with generation, phase and a bounded error code. Failed contenders cannot replace the active owner's diagnostics. A lost start response requires status inspection; it does not authorize automatic restart.

Calls after start select the exact generation. Status can discover it when a start response was lost. Provider calls require both the runtime's allow_provider_calls policy and the request's allow_provider flag. Consequential order/quote methods additionally require allow_trading at both boundaries. An optional exact method allow-list narrows authority. These controls are local admission, not vendor entitlements or a trading risk engine. The binding account_ref is an immutable selection and correlation reference; this profile does not resolve it into an AccountInfo filter or constrain native account parameters. Account permissions remain subject to provider authorization and separately qualified policy.

## Worker and shutdown behavior

One supervised native worker executes an admitted SDK invocation or shutdown. The control thread remains available for status, retained event pages and recovery while that worker is occupied. A new invocation is refused as busy while another is active; a duplicate attempt only reads its existing record. Long calls return in_progress with the attempt identity for subsequent inspection. No timeout causes automatic redispatch or forceful SDK cancellation.

An explicit stop during an active invocation returns stop_blocked_by_active_invocation. When admitted, shutdown runs on the worker and may return stopping before destruction completes; subsequent status distinguishes stopped from stop_failed. A process termination signal requests orderly shutdown after any active invocation finishes. A hung SDK call can therefore leave graceful shutdown pending. These states do not establish provider order completion, cancellation or reconciliation.

## Attempts and uncertainty

Invocation requires an attempt_id. Each private runtime directory admits at most 100,000 retained attempt records; capacity exhaustion refuses new attempts without deleting recovery evidence. The runtime writes an outcome_unknown record and synchronizes it before native dispatch. It then retains the returned SDK result, or unresolved uncertainty after an exception/lost continuation. Reusing an attempt with the same binding/method/parameters returns the retained record without redispatch; a conflicting digest is rejected. A caller's new attempt ID is a new explicit request and must not be used to bypass unresolved recovery. SDK return is not provider completion.

Attempt records remain in the private runtime directory across restarts and are inspectable without a running server. They contain safe correlation and result evidence, not original credential-bearing requests. A loss between dispatch and completion persistence remains unknown. Completion persistence failure preserves the earlier unknown record and blocks further new invocations in that owner until explicit recovery. Attempt inspection can be bound to the expected runtime generation even when the server is absent. No journal can make the provider's nontransactional effect atomic with local disk. Host stop, logout and cancel are different actions; stopping does not cancel or reverse external orders.

## Events and bounds

Runtime callback observation is a bounded memory queue, at most 4,096 events and 4 MiB. Individual observations beyond 256 KiB are marked lost; old records are evicted visibly when capacity is exhausted. Sequence numbers, generation, local observation time, retained cursors and cumulative lost count make gaps detectable. Pages contain at most 256 records and 512 KiB. This control view is not a lossless execution journal or a market-data delivery guarantee. Downstream consumers must reconcile gaps using the applicable provider operations before treating state as complete.

## Version and maintenance boundaries

`knowledge/sqv/srrapiv/BINDINGS.md` and `MAINTENANCE.md` define exact artifact tuples, strategy bindings, directed compatibility, evidence and inventory accounting. Multiple private runtime directories can retain independent selected versions; no mutable latest alias or ambient library lookup chooses a release. The SDK-enabled CMake build selects one explicit platform lane and hashes its entire static vendor-library closure. Runtime admission checks the selected adapter version and executable bytes against the binding, checks operating system and architecture, and, for SDK builds, checks the exact SDK version, compiled header digest and selected library closure digest. Compiler, ABI, dependency and archive metadata remain pinned declarations; these runtime checks do not independently reconstruct or prove those supplied declarations. Their qualification requires separate build and dependency evidence. More than one SDK release requires independently built and qualified native packages. A retained client is not a promise of continued vendor service support.

## Qualification and limits

Focused native and installed command tests exercise the declared local control, serialization, binding, refusal and recovery boundaries. The test-only slow vendor models a blocked invocation and asynchronous shutdown without SDK linkage. The SRRAPIV CI workflow declares SDK-free Ubuntu x86_64, Ubuntu ARM64 and macOS Intel jobs; workflow presence is not evidence that any hosted job passed. An actual SDK compile/link proves that exact target only. Live credentials, sessions, accounts, entitlements, order acknowledgements and vendor conformance require authorized provider testing. SSIAG protected delivery and STAV audit are separate integration contracts; this module does not claim those services merely because it uses local private files. Automatic provider-state reconciliation, certified account risk behavior, a remote runtime carrier and a mandatory research retention path are not supplied by the local control queue. The complete architecture remains the target; discovery reports any native mapping limitation explicitly.
