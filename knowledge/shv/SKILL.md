# Symphony Hardware Vector Skill

## Procedure

1. Resolve the applicable SHV Contract Quad and companion through `MANIFEST.md` and SKVI. Read the selected module contract and exact release admission before constructing input.
2. Resolve exact product, revision, configuration, and evidence source. Separate vendor specification, measured behavior, derived comparison, and user declaration.
3. Record test environment, software versions, time, uncertainty, and conflicts.
4. Keep physical Node identity in SNV and provider offering truth in SCV. Describe hardware capability consequences while preserving the caller's algorithm and composition choices.
5. For implementation changes, keep owner manifests, SKVI routes and existing SSFV records consistent. Run the affected native owner checks; repository-validator success alone does not establish native SKVI or SSFV acceptance. A generated graph remains a disposable projection of the owner records.

## Stop Conditions

Do not infer unsupported hardware facts, namespace equivalence, permission or physical compatibility from structural acceptance. New graph technologies, ontologies, benchmark authorities, scoring formulas, APIs, AI behaviors, probes and engine operations require their own explicit owner contracts before being represented as supported SHV behavior. Existing implemented operations remain available under their selected contracts.

## Initial kernel administration

Read `KERNEL.md` and the exact installed schema before constructing input. Select explicit kernel/adapter prefix and version through `qxctl shv`. Preserve caller-selected coverage, mappings, evidence roots, subjects and requirements. Structural adapter acceptance does not replace `shv graph validate`; unknown whole-system compatibility remains unresolved.
