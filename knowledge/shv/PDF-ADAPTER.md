# SHV bounded PDF adapter v1

This SHV-specific consumer interprets AMD publication 69290 revision 1.00, page 13 / Table 8. SODV publication and SMCV Markdown exchange retain their existing scopes; this module does not claim general document-decoder ownership. Independently installed C++26 shv-pdf-adapter 0.1.0-dev exposes inspect/extract. qxctl shv pdf inspect|extract|verify|schema|template administers every delivered operation and receipt-owned discovery. All require explicit --prefix/--version; extract/verify require --input.

Extract input exactly {source_root,source,decoder_root,decoder,profile}. Source contains id,path,bytes,digest; decoder contains path,digest; paths are safe root-relative regular files. The selected PDF is read without following symlinks and verified against its exact size/hash before decoding. The selected PDFium library is bounded to 64 MiB, checked against its digest before loading and rechecked afterward; qxctl independently checks source and decoder bytes before and after native invocation. A decoder is executable code selected by the caller, not sandboxed document data. Hash checks identify the selected binary; they do not authenticate its publisher or cover all transitive platform dependencies. Loading observations are sequential, not hostile-race-proof execution isolation.

Only profile amd-69290-table8.v1 is implemented. It requires 16 pages, extracts zero-based page 12 through the selected PDFium C API, caps text at 32768 UTF-16 characters and checks publication/revision, table heading and exact column header. CR is normalized out and valid Unicode is retained as UTF-8; malformed surrogates reject. Table rows must have an exact OPN/model/decimal-text shape with unique OPNs and model IDs, exactly 28 rows on the selected page. Missing or ambiguous headers, malformed rows, duplication and bounds violations reject. Row order is preserved. The numeric column is retained solely as source_metric_text; no export or performance calculation is interpreted.

Output symphony.shv.pdf-extraction.v1 retains source manifest, decoder path/hash, profile, page index/count, exact decoded text and digest, interpreted rows, namespace AMD.OPN, namespace_equivalence=not_asserted, documentary_lineages=1 and self-seal. It is a derived artifact of the original PDF, never a second independent vendor document. Go validates strict fields/seals, rederives rows from returned text and checks declared source/decoder bytes; PDF decoding remains owned by the exact selected native implementation. This is not an independent second PDF parser.

Verify input exactly {request,artifact}. It reruns the native extraction against original bytes and the selected decoder, requiring full equality with the supplied derivation. Failure returns no successful verification. Extraction and replay do not write source files, publish a catalogue, silently reinterpret OPN as Product ID Tray or infer physical identity. Callers can retain explicit associations through existing dossiers; any namespace mapping remains a separately visible caller/source contract. Root relocation with unchanged relative paths and identical bytes preserves the extraction identity.

The PDFium implementation is replaceable only by explicitly selecting another binary that supports this adapter’s C API. A different binary changes the derivation identity. No bundled library, automatic install, global decoder, OCR, password-protected source support or arbitrary-layout coverage is added. Process deadline/output bounds follow the existing engine foundation. New document grammars require separately versioned profiles. Existing source/kernel packages and original snapshots remain unchanged.

## Source-replayed assertion graph (adapter 0.2.0-dev)

The new exact adapter version adds native graph_project and graph_validate. Extraction protocol and original table profile are unchanged. Version 0.1.0 remains selectable for its original operations; graph operations require 0.2.0 explicitly. No automatic version substitution occurs.

Graph project consumes an extraction request and decodes original bytes before producing symphony.graph.exchange.v1. The complete extraction remains owner_artifact, owned by symphony-shv-pdf 0.2.0-dev. The graph contains one DocumentSource, one DocumentDerivation and 28 DocumentSubject nodes, and 57 sorted edges. A derivation is linked to its original source; it never becomes another independent vendor source. Subject IDs bind the exact derivation and OPN, preserving document scope rather than merging hardware entities.

Each documents_identifier edge retains predicate=oem_identifier, the exact OPN value, qualifier=issuer=AMD;namespace=opn;profile=1 and a citation with original source ID/hash, derivation hash, zero-based page index 12, table 8 and zero-based row index. An extracts_subject edge identifies the decoding lineage. The original numeric text remains in owner_artifact and is not interpreted as a hardware requirement. No Product ID Tray equivalence or physical identity is asserted.

Graph validate takes exactly {request,graph}, decodes the original again, rebuilds the entire projection and requires exact equality. A structurally valid or resealed graph is insufficient. qxctl independently checks projection correspondence and source/decoder bytes, while native code owns PDF decoding. qxctl shv pdf graph project|validate directly exposes both operations; roundtrip composes source validation, an exact caller-selected generic adapter roundtrip, and source replay of the returned graph. Exact PDF and generic adapter receipts are checked across the composition. Existing generic adapter query remains available for structural retrieval; it does not substitute for owner validation.

These are PDF-owned documentary assertion edges, not a shv-engine catalogue artifact. Existing kernel input profiles remain unchanged. Ingesting these assertions into catalogue evaluation needs an explicit versioned provenance-bearing contract; it must not manufacture an HTML source or silently trust caller-authored claims. Graph storage, canonical publication and namespace equivalence are separate capabilities.
