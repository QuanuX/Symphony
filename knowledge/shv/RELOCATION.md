# SHV source-data relocation and derived jobs

`qxctl shv materialization relocation run|schema|template` relocates source-data roots into a separate derived job. Run requires explicit parent `--job-root/--job-id`, destination `--target-job-root/--target-job-id`, and `--input`. Input exactly `{tasks:[{task_id,source_root}]}`, one entry per parent task in original order, 1–8 tasks. Roots are clean absolute descendants. The operation does not copy files; the caller supplies already-present source bytes at the selected root.

Source-history location, TOPS/source identity, immutable bundle bytes, source/kernel installation, partition installation, coverage, requirements and task order remain pinned. No state-root or engine override is accepted. Relocating a protected authority store or engine installation is a separate future contract. The old bundle_path remains provenance and is never reread.

Hold the parent job lock, validate its retained checkpoint, replay every original bundle using its new source-data root and original protected history/engine owners, and rebuild its partition. If a parent task is complete, its partition must match exactly. Pending parent tasks are replayed and completed in the child; the parent stays unchanged. Sequential replay is not a simultaneous global snapshot.

After all tasks succeed, atomically save a separate fully completed checkpoint with protocol `symphony.qxctl.shv-materialization.v2`. It retains the v1 fields and adds exact `origin:{parent_job_root,parent_job_id,parent_checkpoint_digest,source_roots:[{task_id,from,to}]}`. Origin rows correspond to child task order and endpoints. Every derived task must have a completion. The existing one-MiB JSON bound and no-follow private store mechanics apply. The partition installation is checked before work and at commit. No target state.json is created on replay failure. A crash before the atomic checkpoint can require repeating pure replay work; this operation does not claim per-task progress retention.

The parent is never rewritten. A target cannot be the same job at the same root. A pre-existing target must be the same v2 derivation, including parent checkpoint, endpoints, bundles and partitions. Retry replays all tasks and preserves the stored checkpoint rather than replacing its earlier replay observations. The response carries fresh sequential replay proofs and the retained target checkpoint digest. Changed intent rejects. Parent progress that changes its checkpoint yields a distinct derivation and therefore requires a new target identity.

Output protocol `symphony.qxctl.shv-relocation.v1` contains target job_id, checkpoint_digest, origin, per-task replay proofs, dependency_validation=`sequential_replay`, catalogue_published=false and digest. Discovery is CLI-owned and requires no installation selection. Existing materialization schema discovery now includes strict v1 and v2 checkpoint alternatives; earlier v1 bytes and meanings remain unchanged. Existing status/export/run/resume accept either version. Status validates local lineage correspondence without claiming parent availability, authentication or fresh replay; export replays all child sources again.

This is private evidence orchestration. It does not grant source adoption or catalogue publication authority, acquire source files, change hardware, infer physical compatibility or choose a database. Self-seals establish local integrity, not publisher authentication.
