# SHV document ingestion and caller-owned hardware universes

Kernel 0.3.0-dev extends the existing catalogue build/query, evaluation and graph operations with `pdf_opn.v1`. Older exact kernel versions remain selectable. No competing catalogue or evaluation command is added.

A PDF subject mapping contains id, manufacturer, model, hardware_class, source_id, heading_section=table8, interpretation_profile=pdf_opn.v1, document and fields. Document contains decoder_root and the complete retained symphony.shv.pdf-extraction.v1 artifact. The kernel pins and compiles PDF adapter 0.2.0-dev's C++ reader, including its exact bounded profile, into its own receipt-bound executable. It requires no separately running PDF service. PDFium remains an explicit caller-selected external executable library whose identity is in the derivation; nothing downloads or selects a decoder automatically. This is a supported compiled reader, not a generic dynamic interpretation plug-in loader.

The kernel reconstructs the original extraction request from the catalogue source manifest, source root, retained decoder identity and profile. It decodes actual original bytes and requires complete equality with the supplied extraction. A self-sealed caller artifact is insufficient. Repeated subjects with the same source/decoder/profile reuse one extraction within that invocation; no persistent cache or freshness substitution is introduced. Go independently checks actual source/decoder identities, extraction structure and row correspondence. The complete replayed derivation remains in catalogue mapping and therefore in the catalogue graph's owner artifact.

Each selected field has an arbitrary caller predicate name, label=OPN, next_label=Model, value_type=string, and qualifier=issuer=AMD;namespace=opn;profile=1. The source model must occur in the decoded table. Its original OPN becomes the value, with the original PDF source ID; no intermediate HTML or independent document source is fabricated. Introduced dates remain unknown unless separately evidenced. Model/manufacturer/class labels in the mapping retain their caller-declaration status.

The existing evaluator performs qualified comparisons and leaves a Product ID Tray requirement unresolved against an OPN assertion. Refresh, comparison, dossiers and generic graph exchange retain their existing owners. Partition owner 0.2.0-dev admits an exact kernel 0.3.0-dev dependency; retained partition 0.1.0 is not silently substituted. There is still no physical identity inference, namespace equivalence, canonical catalogue publication or graph database default.

## Reusable class profile discipline

SHV distributes tools, contracts and conformance fixtures, not a prepopulated eight-year vendor atlas. The 2018-onward default is caller-changeable coverage policy. Small representative fixtures demonstrate that inclusion, exclusion, unknown dates and extensions work; users acquire and map their own universes through qxctl.

GPU, memory, storage and network-card profiles share source identity, retained bytes, source/mapping revisions, subject scope, typed predicate/value pairs and explicit qualifiers. Each class supplies its own source-evidenced metric definitions. Candidate profile topics include GPU compute/memory capabilities; memory capacity and operating conditions; storage capacity/interface and workload-qualified measurements; network-card ports/link capabilities, timestamp/offload declarations and driver/firmware dependencies. These are profile-design topics, not asserted vendor facts or a mandatory global field list. Comparable fields must agree on units, precision, operating conditions and value meaning; similarly named values alone do not establish comparability.

New hardware fields are added as typed mapping entries with caller predicate names. They do not require new request-envelope keys or a core-wide taxonomy change. Existing fields can remain mapped or be omitted from a new mapping revision. Earlier catalogues replay against their original mapping and source bytes; omitting a field from a later revision does not erase history. The gate's synthetic GPU/memory/storage/networking-card fixtures demonstrate addition, omission and historical replay using the same engine. Unknown protocol/control-envelope keys and invalid known values still reject; extensibility does not turn malformed control requests into valid ones.

Source location changes continue through existing source plan/history/activation surfaces; mapping changes and changed source bytes remain separate comparison dimensions. Mapping diagnostics, reusable profile packaging and portable universe manifests should reuse these owners in subsequent work rather than introduce overlapping control planes. Canonical publication and durable adapters are the following suite, with DuckDB the recommended SQL default and no selected graph database default.
