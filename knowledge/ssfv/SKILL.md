# Symphony Semantic Feature Vector Skill

## Purpose

Guide every authorized caller in reading, evaluating, proposing, reviewing, and deriving Symphony feature truth without inventing capability claims or displacing adjacent knowledge vectors.

## Required Reading Order

1. `knowledge/ssfv/INTENT.md`
2. `knowledge/ssfv/MANIFEST.md`
3. `knowledge/ssfv/SPEC.md`
4. `knowledge/ssfv/NAMESPACES.md`
5. `knowledge/ssfv/REGISTRY.md`
6. `knowledge/SPEC.md`
7. `knowledge/skvi/SPEC.md`
8. the owning module or vector contracts and implementation evidence
9. `knowledge/sodv/SPEC.md` before proposing publication

## Caller Authority

Any caller may inspect canonical SSFV truth and create noncanonical evidence within effective permissions. After the separately reviewed engine and qxctl surfaces exist, any permission-backed caller may also request bounded checks, comparisons, proposals, and disposable graphs. Caller type does not grant or remove authority.

No caller operation may:

- declare a behavior feature-worthy without evidence and owner ratification;
- infer a feature solely from file size, folder depth, language, symbol count, or marketing interest;
- create boilerplate `FEATURES.md` files in every directory;
- use an implicit glob as canonical source scope;
- treat a generated inventory, graph, summary, or publication as canonical;
- change canonical files through `inspect`, `check`, `diff`, `propose`, or `graph`;
- invent implementation, lifecycle, security, audit, API, deployment, or release state.

## Feature Review Procedure

1. Identify the owner contract and exact implementation or protocol boundary.
2. Apply all five feature-worthiness criteria from `knowledge/ssfv/INTENT.md`.
3. Choose the narrowest valid kind and one primary parent when the candidate is not a root capability.
4. Allocate a stable ID under a registered namespace.
5. State who, what, how, when, where, and why in caller-neutral language.
6. List exact implementation paths and explain each implementation language's role.
7. Record typed relationships and factual distinctions from nearby features.
8. Reference applicable adjacent vectors without duplicating their truth.
9. State evidence and explicit non-claims.
10. Update the owner `FEATURES.md`, SSFV registry, and SKVI in one reviewed change.
11. Record SCLV closure only after real review and merge evidence exists.

## Sparse Placement Rule

Create a `FEATURES.md` file only when at least one ratified feature record is owned by that exact source scope. Parent files summarize owned records and link to children; they do not copy child semantics. Explicit repository-relative paths are required in v1.

## Session and Freshness Rule

A working session begins when the effective caller authenticates and ends on logout or mandatory reauthentication unless the administrator configures a different bounded session policy through the eventual qxctl surface.

Future engine results bind to content-addressed contract and source snapshots. Structural integrity is mandatory. Semantic-freshness enforcement is an administrator-controlled safeguard that may be enabled or disabled without classifying the caller.

## Stop Conditions

Stop and obtain permission-backed owner ratification before allocating a public namespace, changing feature-worthiness criteria, changing stable identity, moving owner scope, weakening structural integrity, enabling canonical apply, selecting persistent graph storage, docking an engine into Maestro, or publishing feature-derived claims.

## Non-Authorization Statement

This skill is procedural contract guidance. It authorizes no engine, qxctl command, feature record, distributed `FEATURES.md` file, canonical mutation, graph database, Maestro state, public documentation, or marketing output.
