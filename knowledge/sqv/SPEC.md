# Symphony Quantitative Vector Specification

## Framework Boundary

SQV components remove repeated engineering work only where Symphony has an explicitly ratified, reusable contract. A user may use, replace, extend, bypass, or combine available components according to the compatibility and authority boundaries of their installation.

A Nest serves a user-selected purpose and may contain many modular sections. The fact that single-purpose hot-path Nests are commonly elegant does not authorize SQV to prohibit another architecture.

## Thermal Boundary

SQV contracts must distinguish hot, warm, cool, cold, and freezing consequences where they matter. Administrative SKV, qxctl, graph, publication, agentic, research, and change-recording mechanisms must not silently become inline dependencies of hot or warm strategy execution.

## Broker and Data Interfaces

Not every execution Nest needs a broker API or data API. Those interfaces are primarily relevant to non-FIX systems and must preserve exact version compatibility when present. A Nest built against version 3 remains version-3-bound until the user explicitly migrates it; a current version 13 does not reinterpret the old contract.

FIX systems approach data, symbol matching, and messaging through their own regulated protocol family and SOOV architecture. Non-FIX API governance and broker/data version lineage remain distinct deferred work.

## Reusable Engines

Historical user-authored engines may later be decomposed by function into reusable example components and reassembled as coherent public engines. The Architect determines their names and approves function-to-vector ownership.

## Non-Authorization Statement

SQV defines no universal feed declaration, symbol universe, strategy schema, broker choice, data path, persistence adapter, exhaust record, synchronous/asynchronous rule, or order behavior.
