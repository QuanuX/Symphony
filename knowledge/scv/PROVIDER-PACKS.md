# Portable provider packs and bounded structured interpretation

Contract companion, version 1. First supplied by the independently installed SCV engines at `0.6.0-dev`. This additive contract preserves the earlier source, corpus, profile and knowledge artifacts. It describes the implemented finite tool; it does not prescribe user topology or admit a provider through a central vendor list.

## Authored portable knowledge

`provider_pack_prepare` is a pure proposal operation. Its exact input is `{pack, fixtures}`. The pack draft contains `protocol: symphony.scv.provider-pack.v1`, `pack_id`, `pack_version`, `authored_by`, `provenance`, `provider`, `profiles`, `structured_profiles` and `fixtures`. The result adds a canonical SHA-256 `digest`. It carries no installation receipt, local state directory, executable selector or active source-head mutation. Author strings and provenance describe submitted authorship; a hash does not authenticate an author or establish publisher endorsement.

`provider` is the existing `provider_onboard` input: provider/family identities, display name and desired source declarations. Preparation reuses that owner to validate its sources. `profiles` contains exact previously sealed `interpretation-profile.v1` mappings; their literal/delimited semantics are unchanged. `structured_profiles` contains the new authored `structured-profile.v1` mappings, protected by the enclosing pack digest. Each has the same metadata, media list and rule metadata as an existing profile, with the structured context/extractor described below and no separate profile digest.

A pack selects at most 16 profiles across both arrays and 128 rules in total. Profile identities and generated claim identities must be unique within that pack. Every profile names a declared source and locator of the pack provider. These are finite artifact constraints; arbitrary provider identities may use the generic SCV engine or the appropriate SCHV/SCEV family engine without changing the provider-specific installed package list.

## Detached conformance cases

The pack retains 1–16 fixture manifests. Each contains `fixture_id`, `label`, `authored_by`, `rationale`, `input_digest`, `expected_claims` and `expected_extractions`. Expectations are explicitly authored. Preparation never derives or substitutes an expected answer from the mapping under test.

A detached fixture input is `{fixture_id, captures, bindings, selection_policy}`. Its digest is the SHA-256 of that entire canonical object. The prepare input's `fixtures` array supplies any bodies needed to resolve a manifest's null `input_digest`; the native engine computes and writes the digest. A supplied fixture with an already selected digest must match it. A precomputed nonnull manifest can travel without its input body. Unlisted or duplicate fixture inputs are rejected. Thus normal production use need not carry a pack's entire historical test corpus or run every case.

Expected claims contain exactly `claim_id`, `subject`, `predicate`, `scope`, `statement_kind`, `value` and `dependencies`. Typed values include an explicit unit or null. Expected extraction entries contain `profile_id`, `capture_digest`, `rule_id`, `claim_id`, `status` (`matched` or `unresolved`) and `reasons`. Tests can therefore distinguish a maximum from a default, an exception from the general case, an authored recommendation from a requirement, and an unresolved selection from a positive assertion. Expected arrays are compared as canonically sorted arrays; identities remain significant and repetitions cannot manufacture another native extraction.

## Explicit evaluation and replay

`provider_pack_evaluate` is a pure query with exact input `{pack, captures, bindings, selection_policy, fixtures}`. Production bindings are `{profile_id, capture_digest}`. They select a subset of the pack's profiles; every selected capture must be bound, and a selected profile may bind only once. Production selection and each selected fixture have their own explicit policy. A fixture policy never silently replaces production policy.

The sealed `symphony.scv.provider-pack-evaluation.v1` result has `domain`, the unchanged `input`, ordinary `knowledge`, `extractions`, `fixture_results`, `conformance`, `limitations` and `digest`. The knowledge's interpreter identity binds the exact pack digest. Rules retain authored subjects, predicates, scopes, kinds, dependencies and units. Existing native knowledge normalization and captured-byte evidence validation are reused. This operation does not infer freshness from a successful extraction: the ordinary knowledge retains original observations and policy for a later evaluation at an explicit query time.

Each fixture result retains authored expected and computed actual arrays with status `passed`, `failed` or `not_run`. Selected failures return evidence rather than aborting the production interpretation. `difference_axes` reports separate claim/extraction differences. Unselected cases have null actual arrays and null axes. `conformance` counts passed, failed and not-run cases; it is never certification, complete provider coverage or a count of independently corroborated facts.

`replay_pack` validates a consuming owner's provider/family scope, recomputes the entire retained evaluation under its recorded owner, compares the exact artifact, and only then releases its ordinary knowledge for native composition. A parent consumer preserves the original owner identity. Independently authored fixtures cannot authenticate an underlying publisher or prove deployed behavior; their purpose is to expose what this selected mapping does and where its expected behavior fails.

## The implemented structured slice

Each structured rule uses `extractor: {kind: json_pointer, pointer, type, unit}` and up to eight typed contexts `{pointer, value}`. The context and extracted node must all match. The JSON Pointer follows the token/escape model in [RFC 6901](https://www.rfc-editor.org/rfc/rfc6901): `~1` selects a slash and `~0` selects a tilde, Unicode is not normalized, and array indices require canonical nonnegative decimal spelling without leading zeros. An empty pointer selects the root. Pointers are bounded to 1,024 UTF-8 bytes and 32 segments.

The bounded document parser preserves source numeric lexemes and original value/context substrings. An integer rule requires an integral JSON token within ±9,007,199,254,740,991. A decimal rule requires a numeric JSON node and produces a canonical exact decimal string of at most 128 bytes; exponent magnitude is bounded at 256. It does not round through binary floating point. A JSON string containing digits remains a string and cannot satisfy a numeric extractor. Boolean/string/reference value types are explicit; references can be recorded as string values when directly selected, but are not dereferenced.

Encountering a `$ref` member on any traversed object, including the selected node, produces `reference_unresolved`; the engine neither resolves local references nor fetches external ones. Missing pointers, noncanonical array indices, mismatched typed contexts, invalid JSON, duplicate keys, excessive depth/node count, oversized anchors and incompatible node types remain unresolved. Duplicate keys invalidate the whole selected document, so member order cannot choose an answer. Document parsing is limited to depth 32 and 8,192 nodes. Captured JSON may contain exact decimal tokens even though the administrative wire retains its integer-only number contract.

A selected capture's complete declared source configuration is compared with the pack's desired declaration. Different authority, scope or locator declarations produce `source_declaration_differs`; matching source/locator labels alone do not prove declaration equality. Failed captures produce no claim. Partial captures follow the explicit existing policy and retain `partial_capture_qualified` when admitted. Unsupported selected media types remain unresolved.

A match establishes a deterministic authored mapping from exact selected bytes. It does not infer negation, exceptions, account eligibility or whether a field denotes a default or maximum. Pack authors must select the relevant fields and contextual qualifiers and supply independent positive/negative cases. The implemented structured slice is JSON Pointer extraction, not a general OpenAPI interpreter, JSON Schema validator, reference resolver or executable rules engine.

## Bounds and consumer checks

Each production selection permits 16 captures and 16 bindings. At most 16 selected detached fixtures are allowed, with 16 captures in aggregate across those fixtures. Each fixture still respects profile/rule and capture-binding constraints. The shared engine request/response, string, JSON-value and deadline bounds also apply; these limits are not a promise that every independent maximum fits simultaneously in one envelope.

C++ owns exact replay and ordinary knowledge interpretation. The Go consumer independently checks input/result and source seals, selected capture bytes, pointer/type/context extraction, full claim and anchor attribution, authored expectations, fixture selection/digests and conformance accounting. It rejects resealed alterations. Its checks supplement native replay rather than claiming to independently reproduce every structural native graph node.

Named runtime cases include `test_provider_pack_producer`, `test_provider_pack_rejects_forged_evaluation`, `test_exact_decimal_lexeme`, `test_fixture_failure_retained` and `test_pointer_escape_and_array_indices`. Go cases include `TestSCVProviderPackConsumerMatchesNativeFixture`, `TestSCVProviderPackConsumerRejectsResealedEvidenceAndConformance`, `TestSCVProviderPackMalformedSelectionsRejectWithoutPanic` and `TestSCVProviderPackIndependentStructuredTokens`. The installed Go case `TestInstalledSCVProviderPackConsumer` requires an exact `SYMPHONY_SCV_COMPOSITION_PREFIX`; its presence is not evidence that a particular installation has been tested.
