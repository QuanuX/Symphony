# SCV recoverable index transfer

Contract v1, September 13, 2026. This qxctl orchestration contract extends [inventory and planning](INDEX-MAINTENANCE.md) using the unchanged C++ DuckDB connector 0.2.0-dev source reader and exact 0.1.0-dev or 0.2.0-dev target writer. It does not add a native connector release, storage schema, provider policy or graph backend.

## Execution and authority

`qxctl scv graph-index transfer --input request.json` takes `{plan,expected_plan_digest}`. `plan` is the complete native `connector_result` from transfer-plan, not its qxctl wrapper. The caller explicitly chooses that plan and exact digest. Required source flags are `--connector-prefix`, `--connector-version 0.2.0-dev`, `--index-root`, `--tops-id` and `--namespace`. Backend defaults to the user-selected DuckDB. Existing private source and target roots must be distinct and non-nested. These are this tool's copy/recovery preconditions, not universal architecture rules.

The command independently validates the sealed native plan, its capacity/accounting, exact selected source installation and scope, then binds source root and target root into an immutable transfer intent. It repeats the native source plan and exact retained semantic-owner queries before reservation and before each destination mutation. Target installation is exact, including receipt, prefix and executable identity. A prior ready plan is neither permission nor a reservation; this explicit invocation requests local evidence copying. No SSIAG grant, STAV append or platform permission assertion is synthesized.

Go owns only local orchestration evidence. Existing independently installed C++ prepare/commit operations own all target intent, snapshot and projection mutations. Prepared source records remain prepared. Committed selections are prepared and then committed. Caller order, selected IDs, original validation time, graph and semantic owner remain fixed. Only target connector identity changes the snapshot and intent seals, exactly as planned. Target source-engine semantics are never moved into SQL or Go.

## Durable journal and recovery

The new empty target root receives `scv-transfer-journal/`, private mode 0700. It contains one immutable sealed `intent.json`, a persistent no-follow `journal.lock`, and adjacent immutable `event-00.json` through at most `event-64.json`. Files are effective-user owned regular 0600 files with a single link. The journal lock serializes cooperating transfers to the same root, including requests from different callers or source roots. A conflicting exact transfer identity is rejected.

Intent binds `{protocol,source_root,target_root,plan,digest}` under `symphony.qxctl.scv-index-transfer-intent.v1`. Each event binds `{protocol,transfer_digest,sequence,previous,phase,operation_id,result_digest,digest}` under `symphony.qxctl.scv-index-transfer-event.v1`. The predecessor is the intent digest or immediately prior event digest. There is no mutable authority head, discovery-based selection or timestamp-based winner. This is noncanonical local evidence, following the existing workflow no-follow/lock/fsync conventions.

For each selected operation, the only chain is `prepare_pending → prepared`, and, only for a committed selection, `commit_pending → committed`. A final `complete` event follows the last operation. Pending events are durable before their external action. Acknowledgements retain exact validated native status digests. Published files are immutable: writes use a private scratch file, file fsync, exclusive atomic rename and directory fsync. `pending.json` is never selected as progress; an interrupted scratch write may be replaced under the exclusive lock. A newly created empty journal with no durable intent can be initialized only while the target otherwise remains empty. Unknown files, nonadjacent events, altered seals and ambiguous progress fail closed. No repair selects or deletes arbitrary evidence.

`transfer-recover` takes the same exact request and source flags and requires the existing durable intent. `transfer` itself also supports exact idempotent replay. Neither operation chooses a new plan or substitutes newer owners/evidence. A lost prepare or commit response leaves a pending event; recovery reobserves the target and repeats the same idempotent native operation. Each recorded acknowledgement must reconstruct from the original plan.

## Observation and completion

Target checks admit only the owned journal and the connector's fixed lock/database/WAL names. Native inventory validates all physical records and projections. Scoped records must equal the exact prefix of planned operations allowed by durable progress; global counts must exclude records in other namespaces. Foreign or missing records, premature commits, altered projections and unexpected directory content block completion. The source connector's compatible inventory reader inspects retained target identities without relabeling them, including an explicit legacy target writer.

Before completion qxctl repeats source revision, exact owners and target observations. Complete means this bounded observation proved the selected target states. It does not reserve either root or promise a cross-database atomic transaction. Noncooperating external writers can change roots after an observation; recovery detects conflicting content, and no cross-root lock or isolation guarantee is made. Read operations may trigger DuckDB recovery/checkpoint writes while leaving the source's logical inventory unchanged.

After a work error, a sealed result reports `incomplete`, the actionable problem, durable progress and the last successfully observed target manifest, when available. That manifest can predate the failing action; it is not a substitute for recovery reobservation. Preflight/journal-integrity errors use the existing nonzero qxctl error envelope. An `incomplete` result is a successful delivery of partial evidence, not successful transfer completion. Callers must inspect `status`.

`qxctl scv graph-index transfer-status --target-root ROOT --transfer-digest DIGEST --json` reads only the exact journal and returns `recorded_complete` or `recorded_incomplete`. It requires no source, connector or semantic-owner availability and never claims that the current target was revalidated. A complete historical journal can remain readable even when subsequent recovery is blocked. This command neither resumes mutations nor deletes evidence.

The result protocol is `symphony.qxctl.scv-index-transfer-result.v1`, containing `{protocol,transfer_digest,source_root,target_root,events,next_phase,next_operation_id,status,problem,target_manifest,digest}`. Exact public structural definitions are in `tools/qxctl/internal/scvtransfer/transfer.schema.json`; copied connector definitions retain frozen v2 bytes at the definition level. Runtime native/Go validation establishes seals and semantics beyond JSON Schema. Existing request/output bounds remain 4 MiB, with at most 16 selected records and 65 progress events; oversized intent envelopes fail before target mutation.

All three commands have stable qxctl identities and reviewed feature bindings. Transfer and recovery are evidence-only mutations; status is read-only. Source/target selection, active graph-head switching, retention, deletion, tombstones, cancellation, operation-ID retirement, migration and automatic cleanup are not provided. The journal is retained with its destination. The test-only `symphony_transfer_fault_test` build provides deterministic interruption barriers; production qxctl contains no environment-controlled fault behavior. Verification is scoped to local macOS amd64 process interruption, not hardware power loss or cross-platform certification.

## Gate schema discovery addition

`qxctl scv graph-index schema --connector-prefix PREFIX --connector-version VERSION [--protocol ID] --json` lists protocol entries or returns the complete self-contained schema and exact definition pointer. Connector definitions are read and hash-checked against the selected receipt; transfer/discovery definitions are embedded in the qxctl executable and labeled `qxctl_embedded`. The `symphony.qxctl.scv-index-schema.v1` envelope seals the installation, entries, schema and digest. Listing local transfer contracts does not mean a legacy connector can serve as the newer source reader. No engine version or frozen SCV schema catalog changes.
