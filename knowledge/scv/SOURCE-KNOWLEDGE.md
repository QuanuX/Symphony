# SCV Source Acquisition and Knowledge Interpretation Contract

## Authority and Initial Scope

The 2026-09-10 Architect direction admits independently installed C++ source-knowledge engines for SCV, SCHV, SCEV, SCHV-AWS, SCHV-AZURE, SCHV-DO, SCHV-GCP and SCEV-CF. The initial implementation is a bounded development increment. It preserves selected provider-native material and explicit interpretations before constructing optional capability projections. It is not a complete provider catalog or general Composer.

SCV owns the source and knowledge semantics below. Family and provider Contract Quads specialize domain scope. `modules/scv-engine/` owns the reusable C++ implementation; each package has its own exact identity and receipt. Adding another source/provider definition need not add provider-specific C++ logic. A new syntax, acquisition method or semantic extractor still requires an explicit adapter or interpretation contract. DIY/owned hardware remains a permitted composition choice without an invented allocated family.

## Identity, Selection and Authority

Source, provider, family and locator IDs are opaque protocol-local tokens of 1–128 ASCII letters, digits, underscore, dot, colon or hyphen. Claim and support IDs are separate nonempty protocol-local strings of at most 512 UTF-8 bytes; source-token grammar is not imposed on them. Generated `native:` content identities are scoped to these graph protocols, not an allocated global identity family. They are not global namespace families, provider accounts, URLs, credentials or permissions. A source's identity survives an explicitly selected locator change; its provider and family remain fixed within that chain. A replacement provider/source starts a new chain. Display names have no identity effect.

The supplied source declaration separately carries publisher, authority role, bounded subject scope, locators and continuity evidence. Unknown authority roles, formats and selectors remain declared text; the engine does not acquire a new parser or treat the declaration as verified publisher authority. Continuity evidence is retained for review, not independently verified by the reducer. A changed publisher, authority role or scope is classified as an authority change; an otherwise changed locator configuration is a relocation. A generation starts at one with no predecessor, then advances by one with the previous exact source digest.

Source configuration, retained capture selection and selected graph state are distinct. An applied source configuration does not refresh evidence, prove continuity, delete an old capture, select a graph or authorize a provider action. A capture retains its exact source revision even when a newer source configuration exists. Private state is not canonical repository truth.

## Pure Source Operations and Protected Persistence

`provider_onboard` validates a bounded provider definition and 1–32 desired source declarations. It returns a candidate definition with interpretation scope `captured-text-and-explicit-assertions`. It does not install an adapter, contact a vendor or establish coverage.

`source_plan` receives an operation ID, current sealed source or null, desired source fields and a reason. It returns a sealed plan containing exact expected state digest, classified change, successor and reason. `source_apply` receives that plan and the current source. It verifies the plan digest, expected state, domain, lineage and exact recomputed transition before returning the successor. `source_status` validates an explicitly supplied source and reports its exact digest.

These are pure owner operations. The word `apply` denotes a validated state transition; the C++ process does not persist it, authenticate a caller or issue an audit receipt. A protected storage adapter must serialize expected-state comparison and commit, preserve the exact engine transition, and record truthful attempt state. qxctl's per-TOPS source administration uses the same engine reducer, rather than reimplementing source semantics in Go.

The storage adapter must distinguish proposal identity, required pre-mutation authorization/audit evidence, attempted commit, confirmed after-state and incomplete closure. The initial source-mutation audit profile requires a committed SSIAG authorization-decision receipt bound to the exact subject, action, resource and stable operation correlation, alongside protected durable intent binding the exact plan and installation before mutation. Local append-forward journal evidence records actual source outcomes. This profile does not require or claim a dedicated source-write STAV event. A retry must inspect the original operation and actual state before doing new work. An authorization decision receipt proves its declared decision; it must not be presented as a receipt for a source write that has not yet occurred. Authenticated SSIAG local peer/grant rules remain unchanged, including caller-neutral policy, expiry and non-transferable local authority. Mere possession of a plan, local JSON, a user/agent label or a valid engine digest does not authorize protected persistence.

The current pure process does not implement a durable corpus store, graph-head selection, source retirement, a general policy engine, arbitrary canonical apply or provider operations. Storage-adapter recovery and acceptance evidence must be stated separately from reducer checks.

## Capture Representation

`capture_import` seals an explicitly supplied capture with exact source revision, locator ID, resolved URI, redirect chain, whole-second UTC observation time, optional upstream revision, media type, body, completeness and issues. It computes UTF-8 body byte size and body digest before the enclosing capture digest. An upstream revision is a declared `{scheme,value}` pair, not the retrieval timestamp or engine version.

This profile accepts at most 65,536 body bytes, eight redirects and 64 issues. Each source declares 1–16 unique locator IDs. Binary artifacts, OCR, Markdown conversion, large multi-artifact manifests and chunk reconstruction are not implemented by this profile. Incomplete or failed captures require an explicit issue. A complete flag is supplied evidence; it does not prove the publisher's entire corpus was acquired. Bound overflow is an error, not silent truncation.

A declared URI requires an explicit scheme and excludes whitespace, control characters and user-info credentials. This is syntax validation, not permission to fetch every scheme. Transport adapters have their own allowlist, network and credential boundaries. A redirect records a retrieval route; it never silently rewrites the source declaration or creates continuity evidence. Offline import cannot claim a live fetch. A conditional response without retained verified bytes cannot become a successful empty document.

`capture_compare` validates both captures and separates source identity, configuration, representation, body and completeness differences. Retrieval-only change does not manufacture a changed upstream fact. Changed configuration or coverage may require reinterpretation even when the body hash is unchanged.

## Native Knowledge and Claims

`knowledge_interpret` consumes exact captures, explicit claims, interpreter version and an explicit selection policy. It retains native text/structure and produces a sealed bounded interpretation. `graph_build` combines compatible knowledge objects into a deterministic graph; parent SCV/family composition preserves native facts and support paths. Graph construction does not infer that similarly named services are interchangeable.

Claims distinguish documented facts, requirements, recommendations, observations, user assertions, inferences and hypotheses. Caller-proposed inference remains conditional because the engine does not validate an arbitrary inference rule. Each carries a subject, predicate, typed value, scope qualifiers, evidence anchors, dependency roles and optional validity bounds. Exact decimal quantities use strings so precision is retained without widening the common process protocol to floating-point JSON. A quote occurring in a capture proves attribution; it does not independently prove the correctness of the interpretation. Native extraction limitations remain visible. Initial native extraction recognizes headings and links in text/Markdown, OpenAPI 3.0/3.1/3.2 document information and operation structure, and JSON Schema Draft 2020-12 named properties. It does not resolve schema references, validate instances, interpret arbitrary selectors, merge entity aliases or establish complete provider semantics.

The primary evidence/support set is conjunctive. Optional alternative support sets are separately sufficient paths and retain separate identities. `support`, `requires` and `scope` dependencies do not become interchangeable. Exact searched-scope dependencies preserve the captures used for absence or coverage reasoning. Cyclic domain relationships are representable; circular justification cannot manufacture grounded support. Repeated quotations or mirrors do not automatically become independent corroboration.

The owner-selected policy supplies admitted statement kinds, maximum evidence age when applicable and the treatment of partial captures. Requirements and unknowns remain qualified by that policy. A user may explore a hypothesis without having it relabeled as documented capability. Disputed evidence and independent support paths must remain inspectable.

## Query, Change and Reproduction

Query, explanation, difference and evaluation operations pin an exact graph and explicit query time. Outputs retain input digests, policy, support paths, typed conflict/coverage information, reasons and validity boundaries. `supported` means supported under the bounded selected evidence policy, not empirical truth, deployment permission or provider-wide compatibility. Missing source coverage, a missing adapter and a proven service constraint are different findings.

The same retained captures, accepted claim inputs, interpreter version, policy and graph inputs must produce the same semantic digest. A new model run is not required for replay. A graph need not change for an observation to expire: current evaluation uses query time and the earliest applicable validity boundary. An old successful result must not be reused outside that boundary.

Source content, interpretation, policy, selected coverage, dependencies and time can each affect downstream results. Difference and explanation outputs preserve these causes; they do not automatically replace the selected graph or execute a remediation. If retained source bytes are unavailable, remaining hashes and lineage do not imply reproducible reconstruction. Exported private graphs remain subject to the user's chosen retention and sharing policy.

## Process, Bounds and Integration

Every domain uses the exact `symphony.knowledge.engine-process.v1` bounded stdin/stdout envelope, the shared digest/path/time mechanics, and its own descriptor. Operation IDs are `engop:symphony:<domain>.<operation>` with underscore separators in wire operation names rendered as dots in the stable ID. These IDs are distinct from SSFV feature IDs and qxctl command IDs. Descriptor input metadata uses `symphony.scv.<wire-operation-with-hyphens>-input.v1`; it selects the exact payload shape in the schema catalog and does not add a protocol field inside that payload. `inspect` has an empty-object payload.

The knowledge profile permits 16 captures, 128 claims, eight support sets per claim, 16 premises per set, 512 native nodes and 1,024 native edges. The common 1 MiB request, 4 MiB response, 65,536-byte string, 32,768-value and deadline limits remain independent. A set fitting a domain count bound may still exceed the common byte/value limit and must be rejected. Runtime acceptance, exact result fields and installed-process evidence are linked from module specifications.

SSFV records actual installed capabilities and explicit administration mappings. SKVI routes current contracts and schemas. The invariant registry binds producer and consumer evidence without claiming test execution from the presence of a test name. SCLV closure follows completed, verified source changes. SODV publication, SACV network APIs, operational credentials, cloud deployment and general Composer synthesis remain separate decisions.

## Protected Source and Graph Selection Profiles

For source mutation, qxctl uses actions `symphony.scv.source.onboard`, `.relocate`, `.authority-change` or `.revise` according to the exact C++ change kind. The resource is `symphony.scv.source:` followed by the untagged SHA-256 of canonical JSON `{tops_id,domain,source_id}`; audience is `qxctl`, scope is `tops:<UUID>`, and the stable operation ID is the correlation ID. The authenticated user-scope SSIAG service evaluates its existing local peer and exact-grant rules. These application actions do not mutate SSIAG policy or add an arbitrary append interface.

The graph selection adapter uses a separate protected graph namespace. It validates the supplied graph through `graph_query`, then binds exact graph bytes, graph identity, expected prior graph digest and exact selection generation, installation and operation to durable intent and the applicable `symphony.scv.graph.select` authorization before atomic selection. Source configuration and graph selection remain independent heads. Graph selection compares required `expected_generation` as well as `expected_graph_digest`, so returning to an earlier graph artifact cannot admit a stale A-to-B-to-A plan. Publication history is contiguous and its selected head must match the exact committed generation. The `select` payload is exactly `{graph,expected_graph_digest,expected_generation}`; graph identity and operation identity are explicit flags. The graph resource is `symphony.scv.graph:` followed by the untagged SHA-256 of canonical JSON `{tops_id,domain,graph_id}` with the same audience and TOPS scope as source administration. Status and recovery use retained state and have no input document. Status reports actual stored selection; recovery cannot claim a commit from a mere proposal or replay an expired/unauthorized mutation. The C++ query remains pure and its descriptor does not claim to select durable state.

Source and graph publication recheck the exact decision and capability expiry at the final publication boundary, after the temporary document is flushed and closed and before atomic rename. An expired grant leaves the earlier head and recoverable intent. This check does not claim an independent distributed revocation protocol or remote authority; the applicable existing SSIAG decision semantics remain in force.

The adapter's exact storage/result schema and executable evidence belong to qxctl's contract. The source/graph data schemas here cannot be used as an authorization token or receipt. No dedicated source-outcome or graph-outcome STAV event, remote identity bridge or cross-host authority is implied by these local profiles.

## Additive Maintained Corpus Profile

Engine `0.2.0-dev` adds the four bounded operations in `knowledge/scv/CORPUS.md` without changing the original thirteen operation payloads or the source/capture/knowledge/graph v1 shapes. Its qxctl adapter retains immutable evidence and recoverable jobs with explicit snapshot identities. There is no selected corpus head or implicit change to the existing protected source/graph selection circuits.
