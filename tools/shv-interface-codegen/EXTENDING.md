# Adding another owner

The shipped SHV owner list is not exhaustive. The registration-driven authoring path accepts caller-owned modules and workspaces without modifying a central list or generator source. It generates mechanical interface metadata; it does not implement or silently admit the new engine's semantics.

1. Create the new owner's Contract Quad (INTENT, MANIFEST, SPEC, SKILL), native handlers, schema and tests in the caller's workspace. Choose distinct owner, engine, operation and feature identities. Choose its qxctl domain according to the highest semantic authority over the operation. Check the existing command registry for collisions.
2. Create OWNER-INTERFACE.json using the v2 shape in any of the migrated five owners as an example. Supply your own namespace, exact current version, operations, contract references, resource paths and embedded dependency identities. No SHV module-name whitelist is imposed. Caller hardware fields and requirements are not described by this mechanical declaration.
3. Preserve prior descriptors in a history document with `descriptors` keyed by exact version. A genuinely new owner starts with `{"descriptors":{}}`. Existing owners preserve complete recorded descriptors and provenance; a metadata-only release must match the latest descriptor's operations and contracts. New semantic operations require an explicit owner-contract extension, not editing a frozen historical release.
4. Create INTERFACE-GENERATOR.json using the registration shape from an existing owner. It selects the declaration, frozen history path and SHA-256 byte digest, Go symbol names, three distinct output paths and any exact embedded compatibility version. Paths are relative to the explicit workspace root. For a new owner, use null embedded_compatibility_version; embedded_macro is an unused valid identifier. The registration is authoring configuration, not a permission grant or signed publisher identity.
5. Run `<authoring-build>/shv-interface-generator --registration /absolute/path/INTERFACE-GENERATOR.json --root /absolute/path/workspace`. Add `--check` for deterministic, read-only comparison. The v2 path delegates to owner_codegen.cpp. No edit to history-lock.json or a fixed owner registry is needed. Existing source/publication v1 generation remains available through its unchanged `--owner` route.
6. Integrate the generated C++ descriptor function, Go metadata and CMake inventory under the new owner's build. Generated files identify their module; a different module or a caller-owned file cannot be overwritten at those destinations. qxctl runtime admission must call that owner's independent result verifier and receipt-owned declaration check. Register any new command once through the existing command/feature ownership workflow. Generation alone never creates an executable, command, semantic verifier, runtime loader or installation.
7. Verify the new owner's native semantics, frozen descriptor parity, generated-file drift, installed declaration tampering, dependency versions and guarded uninstall. If there is an embedded legacy reader, pin its exact version and prove its behavior independently. If a consumer is to accept a new writer, review that admission at the consumer; generation does not grant it.

The regression suite generates an additional `user-sensor-engine` in an isolated root, starting with empty history, without changing generator code. It also proves that generation refuses a caller-owned output. Users remain free to build different adapters or authoring systems; this tool is one supplied mechanism.

## Following a metadata release with a semantic release

Freeze the previous installed descriptor and retain verification of its receipt-owned declaration against its original canonical digest. Changing only the current interface constant must not disable verification of a previously shipped metadata release. Review native dependency admission, independent Go replay, installed schemas and qxctl orchestration together. A semantic release requires an exact new version and explicit consumer review; adding its name to mechanical metadata alone does not establish compatibility. SHV partition/publication 0.4 demonstrate this boundary while retaining 0.3 declaration checks.
